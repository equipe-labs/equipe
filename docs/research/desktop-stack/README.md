# Rust 코어로 바꾸고, GPUI는 실측으로 판정하라

GPUI는 equipe에 "과한(overkill)" 선택이 아닙니다. 티켓 보드, 동시에 스트리밍되는 여러 에이전트 로그, diff/코드 뷰, 터미널 패널은 Zed와 gpui-component가 애초에 만들어진 목적과 거의 같은 워크로드입니다. 기능이 훨씬 많은 Zed 전체가 macOS에서 유휴 시 약 180 MB를 쓴다는 측정치도 있습니다. 따라서 이전 턴에서 GPUI를 "과하다"고 한 판단은 근거가 약했습니다. 함께 권했던 "Tauri 2 + Node 사이드카" 구성에는 더 분명한 결함이 있습니다. Node 사이드카만으로 60–90 MB의 디스크를 더하므로, Tauri를 고른 핵심 이유인 작은 설치 크기가 그만큼 사라집니다. 증거가 가리키는 결론은 세 가지입니다. 첫째, UI를 무엇으로 고르든 **equipe 코어를 Rust로 옮겨 UI 프로세스 안에 넣는 것**이 설치 크기를 줄이는 가장 확실한 수입니다. 둘째, UI는 **GPUI + gpui-component를 1순위**, **Tauri 2(단일 웹뷰, Node 없음)를 대안**으로 두고 1주짜리 측정 스파이크로 정합니다. 셋째, 에이전트 CLI 자체가 메모리 바닥을 정합니다. Claude Code는 유휴 시 약 92 MB, Codex app-server는 약 48 MB의 phys_footprint를 씁니다. 그래서 UI 프레임워크 간 수십 MB 차이는 "빈 앱의 첫인상"에서는 크지만 에이전트가 돌아가는 정상 상태에서는 작은 비중입니다. "무겁지 않다"는 체감은 프레임워크 선택보다 로그 저장 방식, 터미널 수 제한, 리페인트 병합 같은 아키텍처 규율에 더 크게 좌우됩니다.

## "과하다"는 판단은 틀렸지만, 위험은 조직 쪽에 있다

GPUI가 equipe에 맞는지 여부는 기술적으로는 이미 답이 나와 있습니다. Longbridge의 gpui-component(현재 이름은 GPUI Kit)는 **75개 이상의 컴포넌트**를 제공합니다. 가상 스크롤 테이블, 높이가 가변적인 가상 리스트, **Tree-sitter 하이라이팅과 LSP 진단을 갖춘 20만 줄 규모의 코드 에디터**, 마크다운 렌더링, 탭을 끌어 옮길 수 있는 도크 레이아웃이 모두 들어 있습니다(벤더 주장). 릴리스도 거의 매주 나옵니다(v0.6.2 → v0.7.0 → v0.7.1, 2026년 9–10월) ([GPUI Kit](https://github.com/longbridge/gpui-component)). 터미널 패널은 Zed 자체가 쓰는 `alacritty_terminal`을 붙이는 것이 표준 경로입니다. 그리고 GPUI 위에서 alacritty_terminal로 에이전트와 터미널을 다중화하는 Paneflow 같은 선례가 이미 있습니다 ([baeseokjae, 2026-10-01](https://baeseokjae.github.io/posts/native-app-for-coding-agents-rust-gpui/)). 메모리 면에서도 근거가 있습니다. Zed 1.0은 M3 MacBook Pro에서 **에이전트 없이 유휴 시 약 180 MB, 인덱싱 후 약 220 MB, 에이전트 패널을 켰을 때 약 340 MB**였고, 콜드 스타트는 0.42초였습니다 ([Vantaige](https://vantaige.io/blog/zed-1-vs-cursor-vs-vscode-real-benchmark-2026)). 다만 이 측정은 RAM 측정 방식이 명시되지 않았습니다. 바이너리 크기 쪽에서는, 최소 GPUI 네이티브 모듈이 macOS arm64 릴리스 빌드에서 22 MB였고 `strip -x` 후 **17 MB**였습니다 ([gpuix #58](https://github.com/remorses/gpuix/issues/58)). gpui-component hello world는 약 12 MB라는 벤더 주장도 있습니다 ([crates.io](https://crates.io/crates/gpui-component/0.5.0)).

그렇다고 GPUI를 무조건 고르라는 뜻은 아닙니다. 위험은 실재하지만, 그것은 성능이 아니라 조직과 생태계의 문제입니다. 공식 `gpui` 크레이트는 **2025년 10월 0.2.2 이후 crates.io에 한 번도 갱신되지 않았습니다**. 게다가 main 브랜치 README가 요구하는 `gpui_platform` 크레이트는 crates.io에 존재하지도 않습니다 ([crates.io API](https://crates.io/api/v1/crates/gpui), [README](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md)). Zed 측은 Zed 밖 사용자의 요구를 "덜 중시"하고 그런 기능 요청을 커뮤니티 포크로 돌려보냅니다 ([gpui-component #1856](https://github.com/longbridge/gpui-component/discussions/1856)). 그 결과 gpui-ce, GPUI Box, gpui-pre, GPUI Fast로 포크가 갈라졌습니다. GPUI Box 문서가 경고하듯 이 포크들의 타입은 서로 호환되지 않으므로 ([docs.rs gpui-box](https://docs.rs/crate/gpui-box/0.1.1)), 어느 계열에 의존할지 고르는 것 자체가 락인 결정입니다. 그나마 다행인 사례도 있습니다. 2025년 10월 크레이트에서 2026년 중반 버전으로 옮긴 한 앱은 **한 줄짜리 수정 네 개**로 끝났습니다 ([baeseokjae](https://baeseokjae.github.io/posts/native-app-for-coding-agents-rust-gpui/)). 따라서 API 변경 속도는 생각보다 완만합니다.

한국어 사용자에게 더 중요한 것은 IME와 렌더링 품질입니다. 2026년에도 CJK IME 버그가 매달 접수되고 있습니다. 후보창 위치 오류([#64850](https://github.com/zed-industries/zed/issues/64850)), 조합 밑줄 누락([#65453](https://github.com/zed-industries/zed/issues/65453))이 있고, GPUI 자체 `input` 예제에서조차 조합 선택 영역이 어긋나 복사 시 패닉이 납니다([#64389](https://github.com/zed-industries/zed/issues/64389)). 한국어 IME의 한자 키 문제도 열려 있습니다([#46319](https://github.com/zed-industries/zed/issues/46319)). 단색 글리프 아틀라스의 바이리니어 필터링 때문에 **CJK 글자가 유독 흐려지는** 문제도 아직 열려 있습니다([#57777](https://github.com/zed-industries/zed/issues/57777)). 접근성 쪽도 초기 단계입니다. AccessKit 지원은 2026-05-27에 병합되었지만 macOS VoiceOver는 부분적으로만 테스트되었습니다([PR #56065](https://github.com/zed-industries/zed/pull/56065)). 성능 함정도 하나 있습니다. 업스트림 GPUI는 프레임마다 창 전체를 다시 그리기 때문에, 변화가 없는 창도 프레임당 CPU 시간이 **3.31 ms**입니다. Longbridge의 GPUI Fast는 이를 0.19 ms로 줄였다고 보고합니다(벤더 측정) ([gpui-fast](https://github.com/longbridge/gpui-fast)). 실제로 Paneflow는 이벤트 기반 갱신으로 바꾸기 전까지 유휴 상태에서도 초당 6–8회 리페인트했습니다 ([baeseokjae](https://baeseokjae.github.io/posts/native-app-for-coding-agents-rust-gpui/)). 여러 로그를 순진하게 스트리밍하면 계속 리페인트가 일어난다는 뜻입니다. 개발 속도 비용도 있습니다. 첫 빌드에 5–15분이 걸리고, 핫 리로드는 확인되지 않았습니다.

정리하면, 이전 답변의 "과하다"는 표현은 틀렸습니다. 정확한 평가는 "**워크로드에는 잘 맞지만, 포크 선택·IME·빌드 속도라는 조직 비용을 감수해야 하는 선택**"입니다. 이 비용은 측정과 검증으로 위험을 줄일 수 있는 종류입니다.

## 어떤 셸도 이기지 못하는 숫자: 에이전트가 메모리 바닥을 정한다

프레임워크를 비교하기 전에 확인해야 할 사실이 있습니다. equipe가 띄우는 에이전트 프로세스가 전체 메모리의 대부분을 차지합니다. 사용자 머신(Apple Silicon, macOS 26.2)에서 n=1로 직접 측정한 결과는 다음과 같습니다(로컬 측정이라 외부 URL은 없고, 측정 방법은 `ps -o rss`와 `footprint <pid>`입니다). 유휴 상태의 `claude` 2.1.285는 **RSS 192 MB / phys_footprint 92 MB**, 유휴 `codex app-server` 0.154.0은 **RSS 104 MB / footprint 48 MB**였습니다. 같은 조건에서 Node 런타임 자체는 footprint 12 MB, Bun은 6 MB에 불과했습니다. 게다가 Claude를 ACP로 붙이는 경로는 Node 어댑터인 `claude-agent-acp`가 Claude Agent SDK를 거쳐 `claude` 바이너리를 다시 띄우는 구조입니다 ([npm registry](https://registry.npmjs.org/@agentclientprotocol/claude-agent-acp/latest), [Zed docs](https://zed.dev/docs/ai/external-agents)). 에이전트 하나마다 프로세스가 두 개씩 붙는 셈입니다. Claude Code는 메모리가 수 GB까지 불어나는 누수 보고도 반복되어 왔습니다. 500 MB → 4.6 GB([#46931](https://claudeissues.com/issue/46931-bug-memory-leak-claude-code-rss-grows-from-500mb-to-4-6gb-within-minutes)), 시간당 약 +500 MB([#37240](https://claudeissues.com/issue/37240-bug-memory-usage-increases-during-extended-sessions)) 같은 사례가 있습니다. 다만 출처가 이슈 미러 사이트이고, 상당수는 이미 해결된 것으로 표시되어 있습니다.

이 숫자가 의미하는 바는 분명합니다. 에이전트 3개가 돌면 **equipe UI를 빼고도 대략 150–300 MB footprint**가 기본으로 깔립니다. 세션 도중에는 이보다 훨씬 커집니다. 이 상황에서 Tauri와 Electron 사이의 50–150 MB, 혹은 GPUI와 Tauri 사이의 수십 MB 차이는 "앱을 막 열었을 때"의 인상은 크게 바꿉니다. 하지만 정상 운영 중 전체 시스템 부담에서는 작은 비중입니다. 따라서 사용자가 "무겁다"고 느낄 가장 큰 실제 위험은 UI 프레임워크가 아닙니다. **누수하는 에이전트 자식 프로세스**입니다. 이 점에서 equipe만의 차별점이 나옵니다. equipe는 에이전트별 메모리를 UI에 보여 주고, 턴과 턴 사이에 footprint 임계값을 넘은 에이전트를 재시작하며, 유휴 에이전트를 지연 생성하고 종료하는 오케스트레이터가 될 수 있습니다. 이렇게 하면 프레임워크를 바꾸는 것보다 체감 무게를 더 크게 줄일 수 있습니다.

측정 방법도 중요합니다. macOS에서 RSS는 공유 dylib 페이지까지 세기 때문에 phys_footprint보다 2–3.5배 크게 나옵니다(Node 40.6 vs 12 MB). Activity Monitor와 jetsam이 쓰는 지표는 phys_footprint입니다 ([basemind sysres.rs](https://docs.rs/crate/basemind/0.23.1/source/src/sysres.rs)). 그러므로 모든 예산은 **프로세스 트리 전체의 phys_footprint 합계**로 잡아야 합니다. Tauri라면 WebContent, Networking, GPU 헬퍼까지 더해야 합니다.

| 참고: 에이전트 바닥 | `claude` 단일 바이너리 223.8 MB, `codex` 222.7 MB (로컬) | Claude 92 MB, Codex 48 MB footprint (로컬) | 수 GB 누수 보고 다수 ([#46931](https://claudeissues.com/issue/46931-bug-memory-leak-claude-code-rss-grows-from-500mb-to-4-6gb-within-minutes)) | n=1 로컬 측정 |

표에서 읽어야 할 핵심은 세 가지입니다. 첫째, **설치 크기에서는 시스템 웹뷰 계열(Tauri)이 확실히 이깁니다**. 둘째, **메모리에서는 빈 앱일 때만 Tauri가 이깁니다**. 실제 웹 콘텐츠를 올리면 WKWebView/WebKitGTK가 Electron보다 90 MB 이상 더 썼고 ([tauri#5889](https://github.com/tauri-apps/tauri/issues/5889)), Windows에서는 WebView2가 곧 Chromium이므로 빈 앱조차 Electron과 비슷하거나 더 큽니다. 노트의 추론에 따르면, 웹뷰 기반 앱에 로그 패널, diff, xterm을 올리면 프런트엔드를 철저히 관리하지 않는 한 **약 250–500 MB**에 이를 것으로 예상됩니다. 셋째, GPU 렌더링 툴킷은 GPU 드라이버와 컨텍스트 자체가 기본 메모리를 차지합니다. 같은 앱을 egui에서 Slint CPU 렌더러로 옮기자 135 MB가 30 MB로 줄었다는 사례가 이를 보여 줍니다 ([Sarrade](https://trystan-sarrade.com/article/rust-gui-135mb-to-30mb-egui-to-slint/)). GPUI도 Metal/wgpu 위에서 돌기 때문에 이 비용에서 자유롭지 않습니다. Linux에서는 wgpu 초기화 시 쓰지 않는 Mesa GL 스택까지 매핑한다는 이슈도 열려 있습니다([#63327](https://github.com/zed-industries/zed/issues/63327)).

다른 Rust 후보를 탈락시키는 이유는 다음과 같습니다. **Slint**는 메모리 바닥이 가장 낮습니다. 하지만 코드 에디터와 터미널 컴포넌트가 없어 diff와 코드 뷰를 직접 만들어야 하고, IME 버그도 열려 있습니다([#10861](https://github.com/slint-ui/slint/issues/10861)). "뛰어난 기능"이라는 요구와 충돌합니다. **Iced**는 COSMIC 데스크톱이 실전에서 검증했고 0.14에서 핫 리로드와 IME가 추가되었습니다([iced releases](https://github.com/iced-rs/iced/releases)). 하지만 wgpu 비용은 GPUI와 비슷하면서도, gpui-component만큼 개발자 도구용 완성 부품(테이블, 도크, LSP 에디터)이 갖춰져 있지 않고, 1년 주기로 breaking 변경이 옵니다. 그래서 GPUI 포크 리스크를 도저히 감수할 수 없을 때 쓰는 2순위 Rust 대안으로 둡니다. **egui**는 macOS 두벌식 한자 후보창 버그([#7974](https://github.com/emilk/egui/issues/7974))가 있고 GPU 메모리 사례가 불리합니다. **Dioxus Native**와 **Makepad**는 각각 beta 상태와 2.0 전환기라 지금 고를 단계가 아닙니다.

## 프레임워크와 무관하게 메모리를 지키는 다섯 가지 설계

가장 효과가 큰 단일 기법은 **로그를 UI 메모리에 두지 않는 것**입니다. 로컬 측정에서 20만 줄 로그를 JS 객체 배열로 들고 있으면 footprint가 **131 MB**였습니다. 같은 데이터를 파일 기반 SQLite(WAL, cache_size=-2000)에 두고 화면에 보이는 200행만 불러오면 **36 MB**로 약 3.6배 줄었습니다. SQLite가 쓰는 메모리는 바인딩이 아니라 연결당 기본 약 2 MB인 `cache_size`가 좌우합니다 ([SQLite PRAGMA](https://www.sqlite.org/pragma.html)). 그러므로 better-sqlite3, rusqlite, node:sqlite 중 무엇을 쓰든 메모리 결정은 아닙니다. 패턴은 이렇습니다. 코어가 ACP `session/update` 청크를 50–100 ms 단위 트랜잭션으로 묶어 SQLite에 추가합니다. 이때 토큰 단위가 아니라 메시지나 툴 호출 단위로 한 행을 만듭니다. UI는 "id N까지 새 행이 있다"는 알림만 받고, 가상 리스트가 보이는 범위만 id 구간으로 페이징합니다. 실시간 꼬리 부분은 2–5천 줄짜리 링 버퍼로 충분합니다.

둘째, **터미널은 에이전트 패널마다 두지 말고 필요할 때만, 수를 제한해서 만듭니다**. ACP 에이전트는 이미 메시지, 툴 호출, diff 같은 구조화된 이벤트를 내보냅니다. 그러니 에이전트 출력은 하나의 가상 리스트로 렌더링하고, 터미널 에뮬레이터는 사용자가 연 셸 명령에만 씁니다. 이 원칙의 근거로 가장 가까운 선례가 있습니다. Electron 기반 다중 에이전트 오케스트레이터인 Superset은 활성 터미널 GPU 컨텍스트를 16개에서 4개로 줄이고 숨은 터미널을 디스크로 내렸습니다. 그 결과 **JS 힙이 581 MB에서 286 MB로(−51%)** 줄었고, git과 파일 감시 작업을 워커 풀로 옮겨 최악의 UI 멈춤을 82.3 ms에서 28.0 ms로 줄였습니다 ([Superset changelog](https://superset.sh/changelog/2026-07-19-performance-memory-and-load)). 참고로 xterm.js에서 160x24 크기에 스크롤백 5000줄을 채우면 약 34 MB를 씁니다 ([xterm.js buffer issue](https://lightrun.com/answers/xtermjs-xterm-js-buffer-performance-improvements)). alacritty_terminal은 그리드를 1000행 단위로 필요할 때 늘립니다 ([Alacritty commit](https://git.causa-arcana.com/PolytreeDE/alacritty/commit/c1e831dab03bd1a48d2aa0f383aa5aaea2b3632b)).

셋째, **프로세스 수를 최소화합니다**. 구성은 UI 하나, 코어 하나(가능하면 UI 프로세스 안), 그리고 지연 생성되는 N개의 에이전트가 이상적입니다. Node 프로세스 하나가 추가될 때마다 footprint 약 12 MB가 붙습니다(로컬 측정). WebView2는 컨트롤마다 렌더러 프로세스가 하나씩 생기므로 Microsoft도 환경을 공유하라고 권합니다 ([MS Learn](https://learn.microsoft.com/en-nz/Microsoft-edge/webview2/concepts/performance)). 웹뷰 스택을 쓴다면 반드시 웹뷰 하나 안에서 패널을 라우팅해야 합니다. 넷째, **리페인트를 병합합니다**. GPUI는 업스트림에서 창 전체를 다시 그리고, egui도 리페인트마다 UI 전체를 다시 만듭니다 ([egui README](https://github.com/emilk/egui)). 따라서 로그 스트림 갱신은 10–30 Hz로 묶어야 합니다. Paneflow는 PTY 깨움을 4 ms 또는 100 이벤트 단위로 병합해 유휴 리페인트를 0으로 만들었습니다 ([baeseokjae](https://baeseokjae.github.io/posts/native-app-for-coding-agents-rust-gpui/)). 다섯째, diff 뷰어, 언어별 문법, 마크다운 렌더러처럼 무거운 하위 시스템은 **처음 쓰는 순간에 불러오고**, 하이라이팅은 화면에 보이는 hunk에만 적용합니다. 이 부분은 수치 근거가 없는 설계 권고입니다.

## 권고: Rust 코어를 먼저 확정하고, UI는 예산으로 판정한다

이전 답변을 이렇게 수정합니다. **"Tauri 2 + Node 사이드카"는 철회합니다.** Node 사이드카는 디스크 60–90 MB와 프로세스 하나를 더합니다. 그리고 그 비용은 GPUI를 고르든 Tauri를 고르든 똑같이 없앨 수 있습니다. 둘 다 Rust 호스트이므로 **Rust로 다시 쓴 equipe 코어를 프로세스 안에 넣을 수 있기 때문**입니다. 이 이전은 현실적입니다. 공식 Rust ACP 크레이트 `agent-client-protocol`은 3.3.0(2026-10-09)이고, 역의존 크레이트가 133개입니다. 다만 한 달 사이 메이저 버전이 세 번 올라갔으므로 버전을 고정(pin)해야 합니다 ([crates.io](https://crates.io/api/v1/crates/agent-client-protocol)). Rust 코어의 유휴 footprint는 3–10 MB로 추정되지만 아직 측정하지 않은 값입니다. 한 가지 주의할 점이 있습니다. Claude 경로는 Node 어댑터(`claude-agent-acp`)를 거치므로, equipe가 Rust가 되어도 **사용자 머신에서 Node가 아예 사라지지는 않습니다**. 차이는 equipe가 Node를 번들하지 않는다는 것입니다. 어댑터 설치는 ACP 레지스트리 방식에 맡기면 됩니다 ([Zed docs](https://zed.dev/docs/ai/external-agents)). Rust 이전이 당장 부담스럽다면 Bun으로 컴파일하는 것이 중간 단계가 될 수 있습니다. Bun은 유휴 footprint 6 MB로 Node의 절반이지만, 실행 파일이 60 MB이므로 설치 크기 문제는 해결하지 못합니다(로컬 측정).

UI는 **GPUI + gpui-component를 1순위**로 둡니다. 이유는 세 가지입니다. 개발이 macOS 중심이라 GPUI의 가장 성숙한 백엔드(Metal)에 해당하고, 필요한 부품이 거의 다 있으며, 웹뷰 스택에서 부하 시 메모리를 키우는 주범인 JS 힙, DOM, 웹뷰 콘텐츠 프로세스가 아예 없기 때문입니다. **Tauri 2(단일 웹뷰, 가벼운 프레임워크, CodeMirror 6, Node 없음)를 대안**으로 둡니다. Tauri가 더 나은 경우는 팀이 TypeScript UI의 반복 속도와 핫 리로드를 무엇보다 중요하게 여기거나, 스파이크에서 GPUI의 한국어 IME나 CJK 글리프 품질이 받아들일 수 없는 수준으로 확인될 때입니다. 어느 쪽이든 GPUI를 고를 때는 의존 계열을 하나로 고정합니다. gpui-component가 다시 내보내는(re-export) `gpui-pre` 스냅샷을 쓰고, 업그레이드는 팀이 정한 일정에 맞춰 합니다.

| 단계 | 기간 | 내용 | 통과 기준 |
|---|---|---|---|
| 0. 측정 스파이크 | 5–7일 | 두 후보로 같은 화면을 만든다. 구성은 티켓 테이블 하나, 스트리밍 로그 3개(목업 ACP 에이전트가 5만 줄 송출, SQLite 페이징), 에디터 기반 diff 하나, alacritty_terminal 또는 xterm 터미널 하나. Rust 코어는 tokio + rusqlite로 최소 구현 | 아래 예산 충족 여부, 한국어 두벌식 조합·후보창·한자 입력, 유휴 CPU 0%에 가까움, 릴리스 빌드 크기 |
| 1. Rust 코어 이전 | 3–5주 | ACP 클라이언트, 티켓·세션 저장소(SQLite, WAL), 에이전트 수명주기(지연 생성, 유휴 종료, footprint 기반 재시작). 기존 CLI는 같은 코어를 쓰는 얇은 바이너리로 유지 | 기존 CLI 기능 동등, 코어 유휴 footprint ≤ 15 MB |
| 2. UI MVP | 4–6주 | 보드, 다중 로그(가상 리스트 + 링 버퍼), diff 뷰, 에이전트별 메모리 표시 | 예산 유지, 갱신은 10–30 Hz로 병합 |
| 3. 터미널과 CI 게이트 | 2–3주 | 필요할 때만 생성하고 활성 수를 제한하는 터미널. CI에서 시나리오 실행 후 프로세스 트리 phys_footprint 측정(Linux는 PSS) | 회귀 시 CI 실패 |

스파이크의 메모리 예산은 **에이전트 프로세스를 뺀 equipe 자체**만 대상으로 합니다. macOS에서 프로세스 트리 phys_footprint 합계로 잽니다. 목표는 **유휴 ≤ 60 MB, 위 부하 시나리오 최대치 ≤ 150 MB, 압축 설치본 ≤ 30 MB**입니다. 이 숫자들은 증거에서 나온 측정값이 아니라 노트의 CI 예산안과 비교표를 바탕으로 정한 목표치입니다. 측정에는 `/usr/bin/time -l`이 출력하는 "peak memory footprint"와 `footprint -p`를 씁니다. 에이전트 메모리가 섞이지 않도록 반드시 목업 ACP 에이전트로 측정합니다. 판정 규칙은 단순합니다. GPUI가 예산을 지키고 한국어 IME 시나리오를 통과하면 GPUI로 갑니다. GPUI가 예산은 지키지만 IME에서 막히면, 그 버그를 몇 주 안에 우회할 수 있는지 따져 봅니다. Tauri는 부하 시 150 MB를 넘으면 탈락시킵니다. 둘 다 예산을 넘으면 문제는 프레임워크가 아니라 설계 규율에 있다는 신호입니다.

## Conclusion

이번 재검토로 질문 자체가 바뀌었습니다. "GPUI가 과한가"는 핵심 질문이 아니었습니다. 설치 크기를 결정하는 것은 UI 프레임워크보다 **번들된 런타임(Node 사이드카)이 있느냐 없느냐**였습니다. 그리고 실행 중 무게를 결정하는 것은 UI 프레임워크보다 **에이전트 자식 프로세스와 로그·터미널을 다루는 방식**이었습니다. 이 관점에서 보면 Rust 코어는 어떤 UI를 고르든 이득이 되는, 후회 없는 결정입니다. GPUI와 Tauri 사이의 선택은 신념이 아니라 일주일짜리 측정으로 판정할 수 있는 실험이 됩니다.

증거가 가장 부족한 지점은 공교롭게도 이 결정의 중심에 있습니다. GPUI 최소 앱의 실제 RAM, Tauri 2 실제 앱의 헬퍼 프로세스까지 합친 macOS 메모리, 한국어 IME 품질은 모두 공개된 신뢰할 만한 측정값이 없습니다. 그래서 스파이크는 선택 사항이 아니라 이 보고서가 내릴 수 없었던 결론을 대신 내려 줄 수 있는 유일한 수단입니다. 그리고 equipe가 에이전트별 메모리를 보여 주고 제어하는 기능은 "가벼운 앱"이라는 목표를 프레임워크 수준을 넘어 사용자가 체감하는 제품 가치로 만들 기회입니다.
