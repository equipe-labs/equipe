# Move to a Rust core, and judge GPUI by measuring it

GPUI is not an "overkill" choice for equipe. A ticket board, several agent logs streaming at once, diff and code views, and terminal panels are almost exactly the workload Zed and gpui-component were built for. One measurement puts the whole of Zed, with far more features, at about 180 MB idle on macOS. So the earlier turn's judgement that GPUI was "overkill" stood on weak ground. The "Tauri 2 + Node sidecar" setup recommended with it has a clearer flaw: the Node sidecar alone adds 60–90 MB of disk, so the small install size — the main reason for picking Tauri — is lost by as much. The evidence points to three conclusions. First, whatever the UI, **moving equipe's core to Rust and putting it inside the UI process** is the surest way to shrink the install. Second, for the UI, put **GPUI + gpui-component first** and **Tauri 2 (one webview, no Node) as the alternative**, and decide with a one-week measuring spike. Third, the agent CLIs themselves set the memory floor: Claude Code uses about 92 MB of phys_footprint idle, the Codex app-server about 48 MB. So a few tens of MB between UI frameworks is large in "an empty app's first impression" but a small share in the steady state with agents running. Whether it feels "not heavy" depends more on architectural discipline — how logs are stored, a cap on terminals, coalesced repaints — than on the framework chosen.

## "Overkill" was wrong, but the risk is organisational

Technically, whether GPUI fits equipe is already answered. Longbridge's gpui-component (now named GPUI Kit) offers **more than 75 components**: virtual-scrolling tables, virtual lists with variable heights, **a code editor at the 200,000-line scale with Tree-sitter highlighting and LSP diagnostics**, Markdown rendering, and a dock layout with draggable tabs (vendor claims). Releases come almost weekly (v0.6.2 → v0.7.0 → v0.7.1, September–October 2026) ([GPUI Kit](https://github.com/longbridge/gpui-component)). For terminal panels the standard path is to attach `alacritty_terminal`, which Zed itself uses, and there is already a precedent, Paneflow, multiplexing agents and terminals with alacritty_terminal on GPUI ([baeseokjae, 2026-10-01](https://baeseokjae.github.io/posts/native-app-for-coding-agents-rust-gpui/)). There is evidence on memory too: Zed 1.0 on an M3 MacBook Pro was **about 180 MB idle without agents, about 220 MB after indexing, and about 340 MB with the agent panel on**, with a 0.42 s cold start ([Vantaige](https://vantaige.io/blog/zed-1-vs-cursor-vs-vscode-real-benchmark-2026)) — though that measurement does not say how RAM was measured. On binary size, a minimal GPUI native module was 22 MB in a macOS arm64 release build and **17 MB** after `strip -x` ([gpuix #58](https://github.com/remorses/gpuix/issues/58)); the vendor also claims about 12 MB for a gpui-component hello world ([crates.io](https://crates.io/crates/gpui-component/0.5.0)).

That doesn't mean GPUI should be picked no matter what. The risk is real, but it is about the organisation and the ecosystem, not performance. The official `gpui` crate **has not been updated on crates.io once since 0.2.2 in October 2025**, and the `gpui_platform` crate the main branch's README requires does not exist on crates.io at all ([crates.io API](https://crates.io/api/v1/crates/gpui), [README](https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md)). Zed "deprioritises" the needs of users outside Zed and sends such feature requests to community forks ([gpui-component #1856](https://github.com/longbridge/gpui-component/discussions/1856)). As a result the forks have split into gpui-ce, GPUI Box, gpui-pre and GPUI Fast. As GPUI Box's docs warn, their types are not compatible with each other ([docs.rs gpui-box](https://docs.rs/crate/gpui-box/0.1.1)), so choosing which line to depend on is itself a lock-in decision. There is one reassuring case: an app that moved from the October 2025 crate to a mid-2026 version needed **four one-line fixes** ([baeseokjae](https://baeseokjae.github.io/posts/native-app-for-coding-agents-rust-gpui/)), so the API changes more gently than feared.

What matters more for Korean users (and CJK users generally) is IME and rendering quality. CJK IME bugs are still filed every month in 2026: the candidate window in the wrong place ([#64850](https://github.com/zed-industries/zed/issues/64850)), the composition underline missing ([#65453](https://github.com/zed-industries/zed/issues/65453)), and even GPUI's own `input` example mis-tracks the composition selection and panics on copy ([#64389](https://github.com/zed-industries/zed/issues/64389)). The Hanja-key problem of the Korean IME is open too ([#46319](https://github.com/zed-industries/zed/issues/46319)), as is **CJK text looking especially blurry** because of bilinear filtering of the monochrome glyph atlas ([#57777](https://github.com/zed-industries/zed/issues/57777)). Accessibility is early as well: AccessKit support was merged on 2026-05-27, but macOS VoiceOver is only partly tested ([PR #56065](https://github.com/zed-industries/zed/pull/56065)). There is one performance trap: upstream GPUI redraws the whole window every frame, so even an unchanging window costs **3.31 ms** of CPU per frame; Longbridge's GPUI Fast reports cutting that to 0.19 ms (vendor measurement) ([gpui-fast](https://github.com/longbridge/gpui-fast)). Paneflow in fact repainted 6–8 times a second even idle until it moved to event-driven updates ([baeseokjae](https://baeseokjae.github.io/posts/native-app-for-coding-agents-rust-gpui/)) — streaming several logs naively means constant repaints. There is a cost in development speed as well: a first build takes 5–15 minutes, and hot reload was not confirmed.

In short, the earlier answer's "overkill" was wrong. The accurate assessment is "**a good fit for the workload, at an organisational cost — the choice of fork, IME and build speed**". It is the kind of cost measuring and checking can de-risk.

## A number no shell beats: the agents set the memory floor

Before comparing frameworks there is a fact to establish: the agent processes equipe starts take most of the memory. Measured by hand on the user's machine (Apple Silicon, macOS 26.2), n=1 (a local measurement, so no external URL; method `ps -o rss` and `footprint <pid>`): an idle `claude` 2.1.285 was **RSS 192 MB / phys_footprint 92 MB**, an idle `codex app-server` 0.154.0 **RSS 104 MB / footprint 48 MB**. Under the same conditions the Node runtime itself was only 12 MB of footprint, and Bun 6 MB. On top of that, attaching Claude over ACP goes through `claude-agent-acp`, a Node adapter that starts the `claude` binary again through the Claude Agent SDK ([npm registry](https://registry.npmjs.org/@agentclientprotocol/claude-agent-acp/latest), [Zed docs](https://zed.dev/docs/ai/external-agents)): two processes per agent. Claude Code has also had repeated reports of leaks growing memory to several GB — 500 MB → 4.6 GB ([#46931](https://claudeissues.com/issue/46931-bug-memory-leak-claude-code-rss-grows-from-500mb-to-4-6gb-within-minutes)), about +500 MB an hour ([#37240](https://claudeissues.com/issue/37240-bug-memory-usage-increases-during-extended-sessions)) — though the source is an issue mirror site and many are marked fixed.

What these numbers mean is clear. With three agents running, **roughly 150–300 MB of footprint sits there before equipe's UI**, and far more mid-session. Against that, the 50–150 MB between Tauri and Electron, or the tens of MB between GPUI and Tauri, change the impression "when the app has just opened" a lot, but are a small share of the whole system's load in normal use. So the biggest real risk of the user feeling it is "heavy" is not the UI framework: it is **leaking agent child processes**. Here equipe can stand apart: it can be the orchestrator that shows each agent's memory in the UI, restarts an agent past a footprint threshold between turns, and starts idle agents lazily and stops them. That cuts the felt weight more than changing frameworks would.

How it is measured matters too. On macOS, RSS counts shared dylib pages, so it comes out 2–3.5× larger than phys_footprint (Node 40.6 vs 12 MB). Activity Monitor and jetsam use phys_footprint ([basemind sysres.rs](https://docs.rs/crate/basemind/0.23.1/source/src/sysres.rs)). So every budget must be **the sum of phys_footprint over the whole process tree** — for Tauri, including the WebContent, Networking and GPU helpers.

Three things to read from the table. First, **on install size the system-webview family (Tauri) clearly wins**. Second, **on memory Tauri wins only as an empty app**: with real web content, WKWebView/WebKitGTK used 90 MB or more over Electron ([tauri#5889](https://github.com/tauri-apps/tauri/issues/5889)), and on Windows WebView2 is Chromium, so even an empty app is about as big as Electron or bigger. By the notes' reasoning, a webview app carrying log panels, diffs and xterm would reach **about 250–500 MB** unless the frontend is managed rigorously. Third, with GPU-rendered toolkits the GPU driver and context themselves take baseline memory: one app moved from egui to Slint's CPU renderer and went from 135 MB to 30 MB ([Sarrade](https://trystan-sarrade.com/article/rust-gui-135mb-to-30mb-egui-to-slint/)). GPUI runs on Metal/wgpu, so it isn't free of that cost either; on Linux there is an open issue that wgpu's initialisation maps an unused Mesa GL stack too ([#63327](https://github.com/zed-industries/zed/issues/63327)).

Why the other Rust candidates drop out: **Slint** has the lowest memory floor, but no code editor or terminal component, so diff and code views would have to be built by hand, and it has open IME bugs ([#10861](https://github.com/slint-ui/slint/issues/10861)) — at odds with "strong features". **Iced** is proven in production by the COSMIC desktop, and 0.14 added hot reload and IME ([iced releases](https://github.com/iced-rs/iced/releases)); but its wgpu cost is like GPUI's while it lacks gpui-component's finished developer-tool parts (tables, dock, LSP editor), and breaking changes come yearly. So it stays as the second Rust option, for when the GPUI fork risk truly can't be taken. **egui** has a Hanja candidate-window bug with the macOS Korean 2-Set input source ([#7974](https://github.com/emilk/egui/issues/7974)), and its GPU-memory case is unfavourable. **Dioxus Native** and **Makepad** are in beta and mid-transition to 2.0 respectively — not yet at a stage to pick.

## Five designs that guard memory whatever the framework

The single most effective technique is **not keeping logs in UI memory**. Measured locally, 200,000 log lines held as an array of JS objects took **131 MB** of footprint; the same data in a file-backed SQLite (WAL, cache_size=-2000), loading only the 200 rows on screen, took **36 MB** — about 3.6× less. SQLite's memory is set not by the binding but by `cache_size`, about 2 MB per connection by default ([SQLite PRAGMA](https://www.sqlite.org/pragma.html)), so better-sqlite3, rusqlite or node:sqlite is not a memory decision. The pattern: the core appends ACP `session/update` chunks to SQLite in transactions of 50–100 ms, one row per message or tool call, not per token. The UI is only told "there are new rows up to id N", and the virtual list pages just the visible range by id. A ring buffer of 2–5 thousand lines is enough for the live tail.

Second, **make terminals only when needed, a capped number, not one per agent panel**. ACP agents already emit structured events — messages, tool calls, diffs — so render agent output as one virtual list and use a terminal emulator only for shell commands the user opens. The closest precedent backs this: Superset, an Electron-based multi-agent orchestrator, cut active terminal GPU contexts from 16 to 4 and moved hidden terminals to disk; **its JS heap went from 581 MB to 286 MB (−51%)**, and moving git and file-watching work to a worker pool cut the worst UI stall from 82.3 ms to 28.0 ms ([Superset changelog](https://superset.sh/changelog/2026-07-19-performance-memory-and-load)). For reference, xterm.js at 160x24 with 5000 lines of scrollback filled uses about 34 MB ([xterm.js buffer issue](https://lightrun.com/answers/xtermjs-xterm-js-buffer-performance-improvements)); alacritty_terminal grows its grid 1000 rows at a time, as needed ([Alacritty commit](https://git.causa-arcana.com/PolytreeDE/alacritty/commit/c1e831dab03bd1a48d2aa0f383aa5aaea2b3632b)).

Third, **keep the number of processes down**. Ideally: one UI, one core (inside the UI process if possible), and N agents started lazily. Each extra Node process adds about 12 MB of footprint (local measurement). WebView2 creates a renderer process per control, so Microsoft too advises sharing the environment ([MS Learn](https://learn.microsoft.com/en-nz/Microsoft-edge/webview2/concepts/performance)); with a webview stack, panels must be routed inside one webview. Fourth, **coalesce repaints**. Upstream GPUI redraws the whole window, and egui rebuilds the whole UI on every repaint ([egui README](https://github.com/emilk/egui)), so log-stream updates must be batched to 10–30 Hz. Paneflow coalesced PTY wake-ups to every 4 ms or 100 events and brought idle repaints to zero ([baeseokjae](https://baeseokjae.github.io/posts/native-app-for-coding-agents-rust-gpui/)). Fifth, load heavy subsystems — the diff viewer, per-language grammars, the Markdown renderer — **the first time they are used**, and highlight only the hunks on screen. This one is a design recommendation with no numbers behind it.

## Recommendation: settle the Rust core first, and judge the UI by budget

The earlier answer is revised as follows. **"Tauri 2 + Node sidecar" is withdrawn.** The Node sidecar adds 60–90 MB of disk and a process, and that cost can be removed just the same whether GPUI or Tauri is picked: both are Rust hosts, so **an equipe core rewritten in Rust can live inside the process**. The move is realistic: the official Rust ACP crate `agent-client-protocol` is at 3.3.0 (2026-10-09) with 133 reverse dependencies — though its major version went up three times in a month, so it must be pinned ([crates.io](https://crates.io/api/v1/crates/agent-client-protocol)). A Rust core's idle footprint is estimated at 3–10 MB, not yet measured. One caveat: the Claude path goes through a Node adapter (`claude-agent-acp`), so even with equipe in Rust, **Node does not disappear from the user's machine altogether**; the difference is that equipe doesn't bundle Node, and installing the adapter can be left to the ACP registry ([Zed docs](https://zed.dev/docs/ai/external-agents)). If the Rust move is too much right away, compiling with Bun can be a step between: Bun's idle footprint is 6 MB, half of Node's, but its executable is 60 MB, so it doesn't solve install size (local measurement).

For the UI, **GPUI + gpui-component comes first**, for three reasons: development is macOS-centred, which is GPUI's most mature backend (Metal); nearly every part needed is there; and it has none of what grows a webview stack's memory under load — the JS heap, the DOM, the webview content processes. **Tauri 2 (one webview, a light framework, CodeMirror 6, no Node) is the alternative.** Tauri is better if the team values a TypeScript UI's iteration speed and hot reload above all, or if the spike finds GPUI's Korean IME or CJK glyph quality unacceptable. Either way, choosing GPUI means pinning one line of dependencies: the `gpui-pre` snapshot gpui-component re-exports, upgraded on a schedule the team sets.

The spike's memory budget covers **equipe itself, without the agent processes**, measured on macOS as the process tree's summed phys_footprint. The targets: **idle ≤ 60 MB, peak in the load scenario above ≤ 150 MB, compressed installer ≤ 30 MB**. These are targets set from the notes' CI budget proposal and the comparison table, not measurements from the evidence. Measure with the "peak memory footprint" `/usr/bin/time -l` prints and `footprint -p`, always with the mock ACP agent so agent memory doesn't mix in. The rule is simple: if GPUI keeps the budget and passes the Korean IME scenarios, go with GPUI; if it keeps the budget but fails on IME, weigh whether that bug can be worked around within weeks. Tauri drops out above 150 MB under load. If both exceed the budget, that signals the problem is design discipline, not the framework.

## Conclusion

This review changed the question itself. "Is GPUI overkill?" was not the key question. What decides install size is less the UI framework than **whether a runtime is bundled (the Node sidecar)**, and what decides weight while running is less the UI framework than **how agent child processes, logs and terminals are handled**. Seen this way, a Rust core is a no-regret decision that pays off whichever UI is chosen, and the choice between GPUI and Tauri becomes an experiment a week of measuring can settle, not a matter of belief.

The evidence is thinnest, as it happens, at the centre of this decision: a minimal GPUI app's real RAM, a real Tauri 2 app's macOS memory with its helper processes, and Korean IME quality all lack public, reliable measurements. So the spike is not optional: it is the only way to reach the conclusion this report could not. And equipe showing and controlling each agent's memory is a chance to turn "a light app" from a framework-level goal into product value the user feels.
