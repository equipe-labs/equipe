# Desktop performance, October 2026

"지금 equipe desktop 앱의 성능이 좀 떨어져가는 기분인데" — the app felt slower after a day
of features landing. This is what was measured, what turned out to cost, what changed, and
how to measure again.

## How to measure

Everything below can be run again.

- **`EQUIPE_PERF=1`** (any build): once a second while frames are drawn, on stderr,
  `perf frames 58 p50 2.1ms p95 4.0ms max 9.8ms cpu p50 1.9ms p95 3.6ms max 9.1ms` — the
  frame's time on the clock and on the main thread's own CPU (which other processes don't
  inflate). `EQUIPE_PERF=2` adds a `perf frame <wall µs> <cpu µs>` line per frame;
  `EQUIPE_PERF=3` adds `perf why <n> <cause>` — what asked for those frames: a `notify`
  (file:line), an animation frame (file:line), or an animation element (by id). The hook is in
  `vendor/gpui-pre/src/window.rs` (`equipe_perf`, marked `equipe:`).
- **A long day, faked**: `FAKE_HISTORY=2500` gives the PM 2,500 lines of history — Korean
  replies in Markdown with lists, tables and code (Rust, TSX), groups of calls with output and
  diffs, news, screenshots (1600×1000 PNGs), four projects' threads
  (`crates/desktop/examples/fake_daemon/history.rs`). `FAKE_LONG_REPLY=1` makes its streamed
  answer a long one too. With `FAKE_BUSY=1` (four more members at work) and `FAKE_BROWSER=1`.
- **Driving it**: the snapshot build (`--features snapshot`) gained `mark:<label>` (a line in
  the log to cut measurements at) and `scroll:<n>,<dy>` (n wheel turns a frame apart). The
  scenario used: 7 s to settle, 10 s idle, 480 wheel turns up and down the conversation,
  member/project/screen switches, 23 keystrokes in the composer, a 10 s streamed reply, idle,
  the browser panel opened.
- **Stacks**: `sample <pid> 4` at each phase, demangled, main-thread inclusive time per function.
- **Builds**: release, `lto = "thin"`, 16 codegen units, unstripped (for symbols). v0.40.0 was
  built from its tag the same way, with only the `EQUIPE_PERF` hook added to an otherwise
  unpatched gpui-pre 0.3.8, and given the same fake-daemon history and script steps.

**Caveat — the machine was not quiet.** Up to nine agents were compiling on the same 12-core
Mac (load average 7–410 during the work). Wall-clock frame times are therefore unreliable;
the numbers below are main-thread CPU per frame, process CPU, `sample` shares and frame
counts, taken back-to-back on the same machine state, with the load noted. Frame counts also
depend on whether the window happened to be the active one (GPUI caps an inactive window).

## What was found

| # | Cause | Where | Size (2,500-line PM history) | In v0.40.0? | Fixed |
|---|---|---|---|---|---|
| 1 | **Browser panel: wheel turns queued one by one** behind Chrome's ~17 ms per `Input.dispatchMouseEvent` | `browser-host.cjs` input queue | scroll → picture **1.7 s p50, 3.1 s p95, settles 3.2 s after the finger stops** | yes | yes |
| 2 | Every tool call's path canonicalized (`realpath`) on every rebuild of the conversation — each streamed tick | `convo::relative` | while a reply streams, 3–4 % of the main thread at low load, **17–21 % under load** (12–16 ms per 80 ms tick) | yes | yes |
| 3 | "•••" streaming pill animates at the display's rate | `chat.rs` `pulse_pill` | 3 animations asking for a frame every vsync for the whole reply (≈ 52 frame requests/s at 60 Hz, double on ProMotion) | yes | yes |
| 4 | A running call's spinner at the display's rate | `chat.rs` groups, your-turn card | 38–59 full-window redraws/s for as long as a command runs | yes | yes |
| 5 | First code block of a language compiles its tree-sitter queries on the main thread | `render::code::highlight` | 114 ms of main thread in the first scroll; worst frame 24.6 ms CPU | since tree-sitter landed | yes |
| 6 | The board's 10 Hz ticker keeps running after leaving the board while anyone works | `views/board.rs` `ensure_ticker` | 1.9 → 9.7 frames/s, 1.6 → 4.3 % CPU, forever | yes | yes (below) |

What was checked and is **not** a problem at this size:

- **Per-frame cost did not regress.** Main-thread CPU per frame, v0.40.0 vs 0.49.0 back-to-back
  (load ≈ 70–150): scrolling p50 2.7 / 2.6 ms, p95 5.7 / 5.3 ms; typing (keystroke handler +
  frame) p50 2.4 / 2.2 ms; idle frames 2.1 / 2.0 ms. Scrolling frames are mostly GPUI's list
  layout of the rows in view (15 %), text shaping of newly visible lines (6 %) and painting;
  the shell's own render is 4 %.
- Markdown: the prose pass and its 128-entry cache, the code-fence pass and the text view's
  parse are ≈ 1 % of the main thread while scrolling; the text view skips a `set_text` of the
  same string. The list re-measures only rows that changed (`same..n`). The CJK keep-all wrap
  patch (`LineWrapper`) is 0.7 %. Zoom: nothing measurable.
- The slice filter rebuilds the blocks on a change only (by `revision`, which only the
  viewed session's events bump); after fix 2 that rebuild is 0.2–0.8 % while streaming.
- Daemon events are coalesced (80 ms) before a redraw; tooltips keep no timers.
- Sent images are decoded off the main thread, thumbnailed, kept once. Browser frames are
  decoded off the main thread; a hidden panel unwatches, a background window asks 5 fps.
- Memory: 100–175 MB, no leak. A 2-minute soak (8 long replies streamed, scrolling, browser
  panel open) grew 139 → 173 MB and fell back (146 MB) when caches turned over; without new
  replies it stayed flat at 154 MB. v0.40.0: ≈ 125 MB on the same history.
- Switching (handler + the next frame's CPU): member 1–7 + 4–8 ms, project 1–6 + 4–11 ms, to
  the board 0–3 + 8–14 ms (first render of the board), back to chat 0 + 3–5 ms. v0.40.0:
  member 2–4 + 4–5 ms, project 3–5 + 2–3 ms, board 0 + 8 ms.

So the app did not get slower per frame. It got slower where work happens: while a reply
streams and while members run commands (more frames asked for, each rebuild of a long
conversation paying for `realpath`s that grow with the day's history), the first time code of
a language scrolls into view — and, by far the most felt, scrolling a page in the browser panel.

## What changed, and the gain

### 1. Browser panel scrolling (`browser-host.cjs`, `views/browser.rs`)

Measured with a real Chrome (throwaway profile) driven exactly as the host drives it —
screencast `jpeg`, `maxFramesInFlight: 1`, acks paced to 30 fps, one input op after another —
and the daemon → desktop line modelled as the daemon's `Pacer` (credit 2, ≤ 30 fps) over a link
of the given RTT and bandwidth, the desktop drawing each picture (decode ≈ 12 ms + a frame)
before its credit goes back. A trackpad: a turn every 8 ms (120 Hz) for 2 s, then 1 s of
momentum; 361 turns. Page laid out at the panel's 800×900 @2x. Input → picture is from a turn
to the first picture on the desktop scrolled at least that far. Load ≈ 7.

| | RTT / bandwidth | wheel ops run | queued at most | pictures/s | KB each | input → picture p50 / p95 / max | settled after the last turn |
|---|---|---|---|---|---|---|---|
| 0.49.0 | 40 ms / 40 Mbps | 361 | 184 | 17.4 | 255 | **1731 / 3115 / 3251 ms** | **3234 ms** |
| wheel turns added up (host) | 40 ms / 40 Mbps | 177 | 2 | 17.4 | 256 | 197 / 229 / 253 ms | 212 ms |
| + one turn a frame (desktop) + half-size pictures while turning | 40 ms / 40 Mbps | 177 | 2 | 24.5 | 96 | **156 / 185 / 200 ms** | **150 ms** |
| 0.49.0 | 5 ms / 200 Mbps | 361 | 185 | 29 | 255 | 1641 / 3036 / 3172 ms | 3164 ms |
| all three | 5 ms / 200 Mbps | 177 | 2 | 29 | 96 | **98 / 122 / 149 ms** | **78 ms** |

(Each row is one of two runs that agreed within a few ms; the second runs are in the work log.)

- **The cause**: each wheel event became one `Input.dispatchMouseEvent`, and the host runs
  input one op after another; Chrome answers a wheel dispatch after ≈ 17 ms (a frame). A
  trackpad sends 60–120 turns a second, so they queued — 184 deep — and the page kept
  scrolling for seconds after the finger stopped. Network speed hardly mattered (row 4).
- **Host**: a wheel turn still waiting its go absorbs the turns that arrive meanwhile (same
  page and modifiers; position of the latest). Nothing else is merged; order with clicks and
  keys is kept (a non-wheel input ends the merging).
- **Desktop**: the first turn is sent at once, the turns after it added up and sent a frame
  (16 ms) apart — half the messages over SSH.
- **Host**: while the wheel turns, the screencast asks for half the size (a quarter of the
  pixels, 255 → 96 KB a picture at quality 50), and the usual size again 300 ms after the last
  turn. More pictures get through a slow line (17 → 24.5/s at 40 Mbps), and the sharp one
  follows when the page rests. Pictures are placed by their header's CSS size, so a smaller
  one fills the same box.
- **Flow control** was checked and is not RTT-bound at the host: the host acks Chrome's frame
  as soon as it is written to the daemon (local), the daemon keeps the latest frame per page
  and sends only with credit. The credit loop desktop ↔ daemon is RTT-bound (2 in flight), but
  at 40 Mbps the line's bandwidth binds first; credit 3 made no difference (227 ms p50).
- Not done: drawing the last picture shifted by the scroll not yet answered (the
  remote-desktop trick) would hide the remaining ≈ 100–150 ms; it touches the panel's drawing
  that other work is changing.

### 2. Rebuilding a long conversation without asking the disk (`convo::relative`)

Each tool call's target is shown relative to where the member works; when the plain prefix
doesn't match, both paths were `canonicalize`d — two `realpath` syscalls for every Bash
command, search pattern, URL or outside file, for the whole history, on every rebuild (every
80 ms tick while a reply streams; on every switch). Canonical forms are now kept for 2 s
(bounded at 8,192), so a file that appears later is still seen within 2 s.

| main thread while a reply streams | 0.49.0 | fixed |
|---|---|---|
| `Chat::sync` (load ≈ 50–150) | 20.6 % (realpath 16.6 %) | **0.8 %** (realpath 0.0 %) |
| `Chat::sync` (load ≈ 7–17, two runs) | 3.6 % / 3.4 % | **0.2 % / 0.4 %** |
| v0.40.0, same (load ≈ 7–17) | 3.2 % / 4.3 % | |

### 3–4. Animations that redrew the whole window at the display's rate

GPUI redraws the whole window for any animation frame (the shell is the root view; nothing
under it is a cached view), so a 5 px dot pulsing at 120 Hz costs a 2,500-line conversation's
full layout 120 times a second.

- The "•••" pill: its three dots now step at most 20 times a second (`with_max_fps(20.)`; a
  soft 1.2 s opacity pulse looks the same).
- A running call's spinner (and the your-turn card's "sending"): `motion::spinner`, GPUI Kit's
  `Spinner` — same icon, 0.8 s turn and curve — at most 30 steps a second (the sidebar's
  spinner already turns at 10).

| | frames/s | process CPU |
|---|---|---|
| reply streaming, 0.49.0 → fixed (back-to-back, load ≈ 70) | 59.6 → 42.6 | 28.0 % → 19.6 % |
| a command running 6 s, 0.49.0 → fixed (load ≈ 55) | 38.3 → 25.3 | 12.3 % → 8.4 % |
| a command running, v0.40.0 (same) | 58.9 | 16.9 % |

With `EQUIPE_PERF=3` the remaining frames while streaming are the daemon's ticks (≈ 10/s) and
the text view's 150 ms fade of each new piece (≈ 18/s); once the reply is in, frames stop.
GPUI Kit's "thinking" shimmer has no rate cap and still animates at the display's rate while a
model reasons.

### 5. Highlighters made ahead (`render::code::warm`)

Making a `SyntaxHighlighter` compiles its grammar's highlight, injection and locals queries
(tsx the most). The first frame a block of that language came into view paid for it on the
main thread. Two seconds after launch a background thread now makes them for bash, rust,
typescript, tsx, javascript, python and json; the main thread takes one when it first needs
it (or makes it itself, as before, for the others or if it's early).

| first scroll through the history | 0.49.0 | fixed |
|---|---|---|
| main thread in `SyntaxHighlighter::new` | 114 ms | 0 |
| worst frame (CPU) | 24.6 ms | 11.5 ms |

### 6. What turns redraws only where it is (`beat.rs`, `pane.rs`, gpui-pre)

The board started a 10 Hz ticker that turned the sidebar's spinners and pulsed the board's
live dots; it ran on every screen for as long as any member was at work (or so marked), each
tick a whole window drawn again. Before the board was first opened nothing turned the
sidebar's spinners at all (a bug). It also sent held-back actions and counted the undo
toast down.

- **One clock** (`beat.rs`): what turns or counts asks it while drawn, for the view it is
  drawn in — a spinner every step (100 ms, 1.2 s a turn, as before), a live dot every other
  step (the same six strengths), a time counting up (`45s`, `25m`) when its words change
  (a second at most, a minute once it counts minutes), the undo toast at each second. At
  that step the clock notifies that view and nothing else; every ask falls on one 100 ms
  grid, so the sidebar and the board turn in one frame. Nothing drawn asks — nothing
  turning, the window hidden or minimized (macOS sends no frames, so nothing is drawn,
  so nothing asks) — and the clock stops. Under Reduce Motion the spinners stand still.
- **The window's parts are cached views** (`pane.rs`): the sidebar, the screen beside it,
  and the conversation in the chat screen, each drawn from the shell's state. GPUI draws
  a notified view and the views around it again, and lays every other cached view where it
  was: a spinner's step draws the sidebar, the composer's blinking cursor (≈ 2 frames a
  second whenever it has the keyboard, before too) the screen but not the conversation.
- **gpui-pre**, three changes (marked `equipe:`): a cached view is drawn again when any
  entity it read while drawn was notified between frames, not only itself
  (`Window::notified_entities`; `detect_accessed_entities` keeps every entity read, not
  only those new to the frame) — so a pane follows the shell, an input's text, a list's
  scroll without observing each; a cached view inside a cached view drawn again is reused
  when it was visited the frame before (`ViewElementState::drawn_in`; upstream drew all of
  them again, and one not visited holds ranges of an older frame); `EQUIPE_PERF=3` says why
  each cached view was drawn again or reused, and the notified entity's id.
- Held-back actions go out on a timer at their time; the board's own state lost `spin`,
  `pulse` and the ticker. The placeholder breathing while a picture comes and the
  dictation dot were capped at 20 steps a second (they ran at the display's rate).

Measured with the release build as above, `FAKE_HISTORY=2500`, 10 s each: idle on chat
(the board never opened), idle on the board, idle on chat after the board; frames counted
with `EQUIPE_PERF=2`, process CPU from `getrusage` at the `mark:`s (now printed with each).
Three squads of the fake daemon: nobody at work (`FAKE_WORKING=0`), one member at work with
its spinner showing (`FAKE_WORKING=1 FAKE_ASKS=0`), and the default (two at work, both
asking permission — what was measured in the table above: no spinner shows, but the old
ticker ran). Load average 100–150 (other agents building): frame counts are exact,
CPU figures are ±30 %.

| squad | screen | frames/s before → after | process CPU before → after | main-thread CPU a frame (p50) |
|---|---|---|---|---|
| nobody at work | chat | 1.8 → 1.9 | 1.2 → 0.9 % | 3.7 → 2.1 ms |
| | board | 0 → 0 | 0.4 → 0.4 % | — |
| | chat after the board | 1.8 → 1.9 | 1.3 → 0.9 % | 3.7 → 2.1 ms |
| one at work (spinner shows) | chat | 1.9 → 11.1 (spinners turn now) | 1.2 → 3.2 % | 3.4 → 1.9 ms |
| | board | 9.5 → 10.0 | 6.3 → 3.1 % | 5.4 → 2.1 ms |
| | chat after the board | 10.1 → 11.3 | 4.4 → 3.5 % | 3.6 → 2.1 ms |
| default (two asking) | chat | 1.9 → 2.9 | 1.2 → 1.8 % | 4.3 → 2.2 ms |
| | board | 9.5 → 0.1 | 5.1 → 0.7 % | 4.4 → — |
| | chat after the board | 9.6 → 1.8 | 3.9 → 1.0 % | 2.4 → 2.2 ms |

The remaining idle frames are the composer's cursor; with a spinner showing, 10 a second
of the sidebar (with `EQUIPE_PERF=3`: "view … drawn again: notified" for the sidebar's pane,
"reused" for the screen and the conversation). A `sample` of such frames: about half is
the sidebar's layout and render, a quarter painting, the rest GPUI's frame. Turning the spinners
on the chat screen, which never turned there before, costs ≈ 2 % CPU at this load.

Not done: the browser panel (an uncached view) is drawn with every frame of the window
while it is open; a running call's spinner in the conversation (fix 4) draws the
conversation's pane at 30 steps a second; GPUI Kit's "thinking" shimmer still has no cap.
